# Release notes 0.2.0

#### Unstable NixOS base

bitcoinix now uses a single `nixpkgs` input tracking `nixos-unstable` for its system
and packages. `nix-bitcoin.useVersionLockedPkgs` defaults to `true`. Review the
[0.2.0 migration guide](../upgrading/0.2.0.md) for the system
input, package customization, reverse-path filtering, FUSE, I2P validation and
systemd-nspawn changes. Non-flake module imports, disabling version-locked
packages, or overriding bitcoinix's nixpkgs input now also move the formerly
separately pinned unstable service packages with the caller's nixpkgs.

#### PostgreSQL 14 removed

nixos-unstable has removed PostgreSQL 14. Nodes that still use PostgreSQL 14, such as
for BTCPay Server, fail evaluation. By default, this applies to a `system.stateVersion`
from 22.05 through 23.05. Upgrade the databases before you update bitcoinix, see the
[upgrade notes](../upgrading/0.2.0.md#postgresql-14-removed).

#### Unversioned PostgreSQL package moves to 18

nixos-unstable's `pkgs.postgresql` has moved from PostgreSQL 17 to 18. If you set
`services.postgresql.package = pkgs.postgresql;` and run PostgreSQL 17, set
`pkgs.postgresql_17` before you update, see the
[upgrade notes](../upgrading/0.2.0.md#unversioned-postgresql-package-moves-to-18).

#### Package selection cleanup

The generated `pkgs/pinned.nix` file has been removed. Package selection and
local overrides now live together in `pkgs/default.nix`; the public
`legacyPackages.<system>.pinned` paths remain available. The deployment shell and
package imports without an explicit `pkgs` still read the lock file through
`pkgs/nixpkgs-pinned.nix`; non-flake NixOS module imports use the system's `pkgs`.

#### Package updates

- CLBOSS 0.17.2 → [0.17.3](https://github.com/ksedgwic/clboss/releases/tag/v0.17.3).
  It pays a swap invoice only when it matches the swap that it requested. A swap
  started by one version can't be claimed by the other: it ends at its timeout and
  the payment fails back to the node. Finish active swaps before you update or roll
  back. On mainnet, CLBOSS makes no swaps, because its swap provider suspended
  them on 2026-08-03.
- electrs 0.12.0 → [0.12.1](https://github.com/romanz/electrs/releases/tag/v0.12.1)
- charge-lnd 0.3.1 → 0.3.2
- HWI 3.1.0 → [3.2.0](https://github.com/bitcoin-core/HWI/releases/tag/3.2.0)
- extra-container 0.17 → 1.0.1 in the deployment shell. Containers that you build
  with its `extra-container` command no longer reach the host's Nix daemon, see
  [extra-container 1.0.1](0.1.6.md#extra-container-101).
- nginx 1.30.6 → 1.30.7, which fixes nine CVEs, see the
  [nginx changelog](https://nginx.org/en/CHANGES-1.30). A default node isn't exposed:
  nginx serves only the mempool frontend, over plain HTTP on a local address, without
  `alias`. Check your own nginx configuration against the list.

#### Electrs uses the unmodified nixpkgs package

Nixpkgs now supplies electrs' pkg-config and zstd build inputs, so the local
override is no longer needed.

#### TrustedCoin initialization

The pinned TrustedCoin package applies two patches from the
[upstream startup fix](https://github.com/nbd-wtf/trustedcoin/pull/44) to prevent
initialization races and reporting height zero without a block source.

#### krops 1.31.1

The [krops deployment](../install.md#5-alternative-deploy-with-krops-legacy) uses krops
1.31.1 instead of 1.26.2 (see the
[changelog](https://cgit.krebsco.de/krops/tree/CHANGELOG.md?h=v1.31.1)). The commands
of the deployment shell don't change. Behavior changes for existing deployments:

- Names of `extraSources` may contain only letters, digits and `._-`, must not start
  with `-` and must not be `.`, `..` or `.populate`. Other names, e.g.
  `"nixos/networking.nix"`, fail evaluation.
- If the node has `/etc/nixos/flake.nix`, krops runs `nixos-rebuild` with `--no-flake`
  and deploys the synced configuration in `/var/src`.
- If a source's path on the node, e.g. `/var/src/secrets`, is a symlink, krops removes
  the symlink and syncs to that path instead of into the symlink's target. If you
  linked `/var/src/secrets` to an encrypted volume, mount the volume at
  `/var/src/secrets` instead before you deploy. Otherwise krops writes your secrets
  to the file system of `/var/src`.
- krops 1.31 pipes `nixos-rebuild` through `nix-output-monitor` if it's installed on
  the node. The deployment then reports success even if evaluation or activation
  failed. bitcoinix's krops therefore defaults `useNixOutputMonitor` of `writeDeploy`
  to `false`, which keeps the previous output and exit status.
- krops reuses one SSH connection per deployment. bitcoinix patches krops to keep the
  connection's socket in `/tmp`, because the upstream path is too long for macOS or for
  an onion host, which made the deployment fail.

Deploying from macOS failed on the symlinks in nixpkgs and bitcoinix
([nixpkgs#180046](https://github.com/NixOS/nixpkgs/issues/180046)).
`examples/krops/sources.nix` now excludes all of them. If you deploy from macOS, copy
the `filters` of its `nixpkgs` and `nix-bitcoin` sources into your `krops/sources.nix`.

CI now deploys the krops example to a VM.

#### Migration warnings on master

Unreleased configuration migrations now warn without blocking deployment or
requiring acknowledgement. Users following master must review them before
deploying; warnings cannot be acknowledged individually and repeat while
applicable. A `configVersion` newer than the latest finalized release is rejected.
Finalizing the release makes its notices blocking errors until acknowledged. See
the [upgrading guide](../upgrading.md) for the version policy.

#### Signet and testnet4

Set `services.bitcoind.network` to `"signet"` or `"testnet4"` to deploy on a
public test network. Evaluation reports incompatible services and plugins
before deployment. Switching an existing node in place reuses several service
databases. Read the [network-switch warning](../configuration.md#bitcoin-network)
before changing this option.

New LND regtest wallets are initialized with regtest chain parameters.

#### Unbeholden LNURL service

[Unbeholden LNURL](../services.md#receive-payments-with-unbeholden-lnurl) v0.4.0 now has
a native package and service for LND and Core Lightning. It supports Lightning
Addresses, withdrawal vouchers, ntfy notifications and Nostr zaps, with restricted
node credentials and persistent keys.

#### Unbeholden Wallet behind a remote proxy

Unbeholden Wallet only accepted connections from localhost, so `address = "0.0.0.0"`
alone didn't let a reverse proxy on another host reach it. List the proxy's address in
the new `services.unbeholden-wallet.allowedClients` option, see
[Access from another device](../services.md#access-from-another-device).

#### Module options and documentation of each release

The new [module options](../options.md) page lists the options of the bitcoinix
modules with their types, defaults and examples, and can be filtered. It replaces
the search.nixos.org links, which mixed in options of other flakes.
docs.bitcoinix.net serves the latest release at its root, as before, and keeps the
documentation of each release from 0.1.6 on at `/v/<version>/`, for example
`https://docs.bitcoinix.net/v/0.1.6/`. A selector in the menu bar switches between
releases.

#### Migrate from nix-bitcoin guide

The new [Migrate from nix-bitcoin](../migrate-from-nix-bitcoin.md) page describes how to
switch a nix-bitcoin node to bitcoinix: the release pin, the move to NixOS unstable, removed
services and the configuration migrations from nix-bitcoin's `configVersion` on.

#### Bitcoin network selection

Select the Bitcoin network with `services.bitcoind.network` instead of
`services.bitcoind.regtest`. The `makeNetworkName` helper
is replaced by `nix-bitcoin.lib.networkName`, which accepts name overrides and
passes other network names through unchanged. See the migration instructions for
[selecting a network](../upgrading/0.2.0.md#bitcoin-network-selection) and
[overriding network names](../upgrading/0.2.0.md#network-name-overrides).

#### Regtest onion target port

The regtest onion service now forwards to port `18445` by default, matching
Bitcoin Core. See the [upgrade note](../upgrading/0.2.0.md#regtest-onion-target-port)
if you maintain a custom Tor mapping.

#### Mempool regtest support

Mempool's backend and frontend now follow `services.bitcoind.network`, including
regtest. See the [0.2.0 upgrade notes](../upgrading/0.2.0.md#mempool-follows-the-selected-network)
for existing regtest deployments and custom frontend settings.

#### Group read access to new bitcoind block files

With `services.bitcoind.dataDirReadableByGroup`, the bitcoind group can now read the
block files and block index files that bitcoind creates while it runs. Before, the
group could read only the files that existed when bitcoind started, and none on
regtest. Before each start of bitcoind, the new `bitcoind-group-read` service sets a
default ACL on the blocks dir. This needs POSIX ACL support on the filesystem of the
blocks dir. Without it, the service logs a warning, and bitcoind still starts. Where
the blocks dir, the files in it or the dirs above it already have an ACL, the service
adds the group's rights to it, and all other users and groups keep their effective
rights. Before, such an ACL could keep the group out and give the others more rights.
If the blocks dir is a symlink, the group can't read new block files anymore. The
`services.bitcoind.sysperms` option has been removed, because Bitcoin Core ignores it.
See the upgrade notes on
[a symlinked blocks dir](../upgrading/0.2.0.md#group-read-access-needs-a-real-bitcoind-blocks-dir)
and [the removed option](../upgrading/0.2.0.md#bitcoind-sysperms-option-removed).

#### Custom RPC users' password HMACs are in the Nix store

The `passwordHMAC` of each custom RPC user in `services.bitcoind.rpc.users` is
written to the world-readable Nix store. Any local user can read it and test password
guesses offline. This isn't new, but it wasn't documented. If a custom RPC user has a
weak password, replace it with a long random one. See
[Allow bitcoind RPC connections from LAN](../configuration.md#allow-bitcoind-rpc-connections-from-lan).

#### Own RPC users for Core Lightning and mempool

Core Lightning and mempool added `getblockfrompeer` and `gettxoutsetinfo` to the
whitelist of the shared `public` RPC user, so every other service of that user
could call them too. They now connect to bitcoind as their own users, `clightning`
and `mempool`, and the `public` user keeps the base whitelist. Setups that supply
secrets themselves need the secrets of the new users, and setups with bitcoind on
another node also need the users there, see the
[upgrade notes](../upgrading/0.2.0.md#own-rpc-users-for-core-lightning-and-mempool).

#### Backups leave out the Lightning channel databases

The backups service copied the channel databases of lnd and Core Lightning while the
daemons wrote them. Such a copy can be torn, and a node that runs from an outdated
copy can lose all funds in its channels. The backup now leaves these databases out.
It still has the files that recovery needs: the lnd seed and `channel.backup`, and
Core Lightning's `hsm_secret` and `emergency.recover`. See
[Backups](../services.md#backups) and the
[upgrade notes](../upgrading/0.2.0.md#backups-leave-out-the-lightning-channel-databases).

#### Backups include consistent copies of bitcoind wallets

Before each backup, the new `bitcoind-wallet-backup` unit asks bitcoind for a copy
of each loaded wallet in `/var/lib/bitcoind/wallet-backups`. A copy of the wallet
file itself can be torn, because bitcoind writes it while the backup runs. If a copy
fails, or bitcoind is starting or stopping, the `duplicity` unit fails after the
backup. See [bitcoind wallets](../services.md#bitcoind-wallets) and the
[upgrade notes](../upgrading/0.2.0.md#backups-include-copies-of-bitcoind-wallets).

#### Backup password and migrated lnd seed

With `nix-bitcoin.generateSecrets`, the backups include the password that decrypts them,
`backup-encryption-password` in the secrets dir. Keep a copy of it off the node. If you
migrated lnd from another node, the `lnd-seed-mnemonic` on the node may not hold the
seed of your wallet. See
[Migrate existing services to bitcoinix](../configuration.md#migrate-existing-services-to-bitcoinix).

#### Core Lightning data dir no longer writable by its group

The Core Lightning data dir now has mode `0750` instead of `0770`. Before, members of
the clightning group could write to it. So they could replace the config that
lightningd loads, or the network dir with `hsm_secret`. Group members keep the RPC
socket, which gives full control over the node. See
[Upgrading to config version 0.2.0](../upgrading/0.2.0.md#core-lightning-data-dir-no-longer-writable-by-its-group).

#### clightning requires the mount of its local replica

With `services.clightning.replication.local.directory`, `clightning` now doesn't
start while the disk or share under that directory isn't mounted. Before, it wrote
the replica to the filesystem below the mount point, usually the primary disk, without
a warning. This works only for mounts that systemd knows, like `fileSystems` entries.
See [Upgrading to config version 0.2.0](../upgrading/0.2.0.md#clightning-requires-the-mount-of-its-local-replica).

#### lnconnect-clnrest finds clnrest's certificate in a custom dir

`lnconnect-clnrest` now asks clightning for clnrest's cert dir, like RTL does. Before,
it always read `server.pem` from clightning's network dir. So with `clnrest-certs` set,
it failed or put the wrong certificate into direct connection URLs. Regenerate such URLs.
When clightning doesn't answer, for example because it's stopped, `lnconnect-clnrest`
prints a warning and uses the network dir, as before.

#### bitcoinix creates the BTCPay Server admin account

BTCPay Server makes the first account that registers the server admin, so any local
user could take the admin account and the internal Lightning node until you registered.
When BTCPay Server has no admin, bitcoinix now creates the admin account `admin@localhost`
first, with the password in `$secretsDir/btcpayserver-admin-password`. Existing admins
stay, so check that they're yours. See the
[upgrade notes](../upgrading/0.2.0.md#btcpay-server-admin-account).

#### BTCPay Server's access to the Lightning node

With `services.btcpayserver.lightningBackend = "clightning"`, BTCPay Server has full
control of the Lightning node, including its funds. With `lnd`, it gets a restricted
macaroon. See [Lightning backend](../services.md#lightning-backend).

#### NBXplorer RPC password permissions

BTCPay Server can no longer read NBXplorer's bitcoind RPC password. Only NBXplorer's
user can read it now. Before, BTCPay Server could read it through the group that
gives it NBXplorer's API cookie. See
[Upgrading to config version 0.2.0](../upgrading/0.2.0.md#nbxplorer-rpc-password-permissions).

#### Charge-LND credential paths

Charge-LND reads its certificate and macaroon directly, without staging them
under a synthetic mainnet directory. Users selecting custom credentials with
`--lnddir` should follow the [0.2.0 upgrade notes](../upgrading/0.2.0.md#charge-lnd-credential-paths).

#### RTL gets its own lnd macaroon and clightning rune

RTL used lnd's admin macaroon and clnrest's admin rune. Now it gets a macaroon
(`services.lnd.macaroons.rtl`) that allows only the lnd RPCs that it calls, and a rune
that allows only the clightning methods that it calls. RTL can still send funds and
open and close channels, but it can't bake macaroons, create runes, stop lnd, delete
lnd's payment history or use lnd's signer RPCs. The macaroon's permissions for the
RPCs of `invoicesrpc` and `walletrpc` use the new option
`services.lnd.macaroons.<name>.optionalPermissions`, so RTL also starts with an lnd
package that lacks these build tags. bitcoinix creates the rune once, at
`rtl-rune` in clightning's network dir. When an update changes the methods that RTL
needs, RTL's start creates a new rune and revokes the old one. RTL's start replaces its
copies of the admin credentials, or removes the copy of a backend that RTL doesn't use.
The admin macaroon and the admin rune themselves stay valid. See
[RTL's backend credentials](../services.md#backend-credentials). An app that reads
RTL's copies needs its own credentials now, see the
[upgrade notes](../upgrading/0.2.0.md#rtl-gets-its-own-lnd-macaroon-and-clightning-rune).

#### systemd holds RTL's port while RTL is stopped

Without netns-isolation, any local user could take RTL's port while RTL was stopped,
for example during maintenance of lnd or clightning, and collect the RTL password
with a fake login page. RTL now listens on a unix socket, and systemd holds
`services.rtl.address` and `port` from boot on with a socket unit, `rtl-proxy-*.socket`.
`rtl-proxy.service` forwards each connection to RTL. The address must be a numeric IP
address without a zone ID, or the system build fails. All clients now share RTL's login
lockout. The first switch to this version leaves the port free for a moment. With
netns-isolation, RTL listens on its namespace's address as before. See
[Upgrading to config version 0.2.0](../upgrading/0.2.0.md#systemd-holds-rtls-port-while-rtl-is-stopped).

#### The secure-node preset turns off SSH password login

The `secure-node.nix` preset now turns off SSH password and keyboard-interactive login
by default, so its sshd onion service accepts only keys. See
[Upgrading to config version 0.2.0](../upgrading/0.2.0.md#the-secure-node-preset-turns-off-ssh-password-login).

#### hardened-extended ignores router advertisements on new interfaces

The `hardened-extended.nix` preset set `net.ipv6.default.accept_ra`, which doesn't
exist, so it had no effect. It now sets `net.ipv6.conf.default.accept_ra = 0`, so the
kernel ignores IPv6 router advertisements on interfaces that appear after the sysctl
settings are applied at boot. Interfaces on which dhcpcd or systemd-networkd handle
router advertisements are unaffected. Others, for example a VLAN with `useDHCP = false`
or any interface with `networking.dhcpcd.IPv6rs = false`, no longer get an IPv6
address or default route from router advertisements. A migration notice lists the
options, see the
[upgrade notes](../upgrading/0.2.0.md#hardened-extended-ignores-router-advertisements-on-new-interfaces).

#### Hardware wallet access requires group hardware-wallets

The Ledger and Trezor udev rules of `services.hardware-wallets` no longer let the
user of the active local session use the device, so only members of group
`hardware-wallets` can use it. The Ledger rule now matches every Ledger device, not
only product `0001`. See
[Upgrading to config version 0.2.0](../upgrading/0.2.0.md#hardware-wallet-access-requires-group-hardware-wallets).

#### Trezor Bridge runs only on request

The Trezor Bridge (`trezord`) no longer runs by default.
`services.hardware-wallets.trezorBridge` turns it on, and then every local user can
use the device through it. See
[Upgrading to config version 0.2.0](../upgrading/0.2.0.md#trezor-bridge-runs-only-on-request).

#### `nix-bitcoin-wg-connect` no longer looks up the public IP

`nix-bitcoin-wg-connect` from the WireGuard preset now needs your node's address as an
argument. Before, it looked up the public IP through public IP lookup services over
clearnet when you passed no address. See
[Upgrading to config version 0.2.0](../upgrading/0.2.0.md#nix-bitcoin-wg-connect-needs-the-nodes-address).
